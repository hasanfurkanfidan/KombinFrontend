# Kombin mobile — agent guide

Kombin is a mobile app that learns a user's style(s), manages their wardrobe, suggests outfits, compares prices across Turkish retailers (Trendyol, Hepsiburada, brand sites) and redirects users to buy through affiliate links. **The app never sells anything itself.** The backend is a .NET Minimal API (`../kombin-backend`); its contract is `docs/openapi.json`.

This repo is the Expo (React Native) client. Implemented so far:

- shared foundation (theme, navigation, API client, session);
- **Auth** (register, login, **Google and Apple sign-in**, session persistence, token refresh, logout);
- **Catalog** (Keşfet product list with filters, product detail with offers and price history);
- **Personas & onboarding** (two steps: audience → 8-card swipe, the style is created as "Tarzım"; the "Tarzım: Ofis ▾" control on Keşfet; match scores);
- **Saved products** (bookmark on cards and detail, Kaydedilenler grid);
- **Price/stock alerts** (alert sheet on detail, **Fiyatlar** tab with stats, status lines and swipe-to-delete);
- **Profile** (persona list and actions) and the **size map** (measurements, per-brand sizes, size hint on detail);
- **Buying** through the backend `/go` redirect;
- **Push** (permission, Expo push token, device registration, foreground banner, tap routing; see below);
- **Notifications** (bell badge on Keşfet, notifications screen, preferences sheet);
- **Analytics** (batched event client, anonymous id, see below);
- **Wardrobe** (Dolap tab, photo add flow, confirm sheet, item detail) and **Outfits** (daily outfit, how-to-wear, saved outfits, the "Bugün için" / "Yarın için" card on Keşfet and on top of Dolap); see below;
- **Social** (the **Akış** tab, post flow with consent and tag editor, creators and profiles, "Gönderilerim", "Kazançlarım", "Engellenenler"); see "Social" below.

Nothing else exists yet (visual search); do not scaffold screens for features the backend does not have.

## Stack and hard constraints

- Expo SDK (managed workflow, **no `expo prebuild`**, no custom native modules), TypeScript `strict`, **Expo Router**.
- Server data: **TanStack Query**. Client state: **Zustand** (session, local prefs, the wardrobe add queue, toasts). No Redux, no MobX, no context-based global stores.
- Styling: plain `StyleSheet` + the central theme. **No Tailwind/NativeWind, no UI kit** (Paper, Tamagui, …). Components are custom and live in `src/components`.
- HTTP: `fetch` wrapped in **one** typed client, `src/api/client.ts`. No axios.
- Tokens: access token in memory (Zustand), refresh token in `expo-secure-store`. **Never `AsyncStorage` for tokens.**
- Forms: `react-hook-form` + `zod` (`@hookform/resolvers` is the glue). Validation messages are Turkish.
- Charts: one small custom SVG chart (`react-native-svg`). No charting library.
- Lint/format: ESLint (`eslint-config-expo`) + Prettier. `npm run lint` (zero warnings) and `npm run typecheck` must pass.
- Tests: Jest (`jest-expo`) + React Native Testing Library.
- All code, comments and docs are English. **All user-facing copy is Turkish** and lives in `src/i18n/tr.ts` (one flat object, no i18n library).
- Do not add a package unless it is strictly required; say why in the PR/summary. Added for personas/alerts: `expo-notifications` + `expo-device` (push permission and token), `react-native-gesture-handler` + `react-native-reanimated` + `react-native-worklets` (the swipe deck and swipe-to-delete rows; `worklets` is reanimated 4's required peer). Added for the wardrobe: `expo-image-picker` (camera and multi-select library, with Turkish permission strings in the `app.json` plugin entry) and `expo-image-manipulator` (resize to 1600 px / JPEG 0.85 before the upload). Added for the photo upload (task 13b): `expo-file-system` (imported from `expo-file-system/legacy`, where SDK 58 keeps `uploadAsync`/`getInfoAsync`): the re-encoded file is streamed from its URI with a binary `PUT` and its size comes from `getInfoAsync`. A `fetch(uri).blob()` body is **not** used: on React Native it can upload something other than the file bytes while storage still answers 200.
- Task 16a (social sign-in) added exactly three: `expo-dev-client`, `@react-native-google-signin/google-signin` and `expo-apple-authentication`. They contain native code, so **the app no longer runs in Expo Go** (it still never uses `expo prebuild`; EAS builds the native project from `app.json` plugins): the development target is a development build, see "Development build" below.
- Task 14 (social) added no package: the photo picker, the re-encode and the upload are the wardrobe's (`expo-image-picker`, `expo-image-manipulator`, `expo-file-system/legacy`).
- Installing those needed `npm install --legacy-peer-deps` once (npm tried to resolve the optional `react-dom` peer to a version that wants a newer React). Afterwards a plain `npm install` works.
- `jest-expo` 58 needs `@react-native/jest-preset` as a peer. An install with `--legacy-peer-deps` skips peers and prunes it, and then `npm test` dies with "The React Native Jest preset ... has moved". Restore it without touching the manifest: `npm install --no-save --legacy-peer-deps @react-native/jest-preset@0.88.1`.
- The notifications preferences have no native time picker (it would need an extra package for one setting): quiet hours use two `Stepper`s per time (`features/notifications/TimeStepper`).

## Layout: `app/` vs `src/`

- `app/` holds **Expo Router route files only** (groups: `(tabs)` with the five tabs `index` (Keşfet), `feed` (Akış), `wardrobe` (Dolap), `prices` (Fiyatlar), `profile`, plus the redirects `tracking` → `/prices` and `add` → `/outfits/daily` that have no button; `(auth)` modal, `(onboarding)` modal; plus `product/[id]`, `profile/sizes`, `notifications`, `wardrobe/[id]`, `outfits/{daily,how-to-wear,saved,[id]}`, `posts/{new,mine,[id]}`, `users/[id]`, `creators/[handle]` and `profile/{sizes,creator,blocks}`). A route file wires a route to a screen component from `src/` (usually a one-line re-export). No logic, no UI, no styles in `app/`. The one non-trivial file is `app/_layout.tsx`, and even that only composes `src/components/AppProviders`.
- All logic and UI live in `src/`:
  - `src/theme` — tokens, spacing, typography (`import { theme } from '@/theme'`).
  - `src/api` — `client.ts`, `endpoints/*`, `queryKeys.ts`, `queryClient.ts`, `models.ts`, `types.gen.ts` (generated).
  - `src/session` — Zustand `sessionStore`, secure-store `tokenStorage`, `useSession` (bootstrap, sign-in/out helpers).
  - `src/features/<feature>` — screens, components and hooks of one feature (`auth`, `catalog`, `onboarding`, `personas`, `saved`, `alerts`, `tracking`, `sizes`, `profile`, `notifications`, `wardrobe`, `outfits`, `social`).
  - `src/push` — permission, token, device registration, `PushLifecycle` (registration on cold start/sign-in, foreground banner, tap routing). `src/session/prefsStore.ts` — small Zustand store for local preferences.
  - `src/analytics` — event queue, allow-list guard, anonymous/session ids, `AnalyticsTracker` (see "Analytics" below).
  - `src/components` — shared, feature-agnostic UI (`Button`, `TextField`, `Chip`, `Screen`, …).
  - `src/i18n/tr.ts`, `src/utils`.
- `@/` is an alias for `src/` (tsconfig paths + Jest `moduleNameMapper`).
- Tests live in `__tests__/` and mirror `src/`.

## Glossary and the clarity rules (Task 15b-A)

Every user-facing string follows `docs/design/glossary.md`; `__tests__/i18n/glossary.test.ts` scans `tr.ts` and fails on a banned word. The short version:

- **Fiyatlar** is the price tab (tracking a price is "izlemek"); **Akış** is the feed tab and appears nowhere else; feed modes are **Herkes / Takip ettiklerim**; "Takip et / Takip ediliyor" is only ever about people. "Keşfet" is only the products tab.
- **Sana uygun %N** (never "uyum" alone), **Tarzım / tarz** (never "persona"), **Bununla giyilir**, **Dolabında var**, **En düşük fiyat**, **Tahmini beden: L**, **Kreatör**, **Paylaş**, **Parça**, **Kombin**, "eşi yok" for an unpaired piece, "Dolaptan çıkar" / "Tarzı kaldır" (not "arşivle"), "Hazırlanıyor" (not "işleniyor").
- Banned: persona, uyum (alone), komşu / vurgu / nötr / tonal, eşleş-, akış in a sentence.

The five rules every screen keeps (audit: `docs/design/clarity-audit.md`): the title plus **one** primary action explain the screen; at most two rows of controls before content; everyday Turkish; every number has a noun or verb next to it; each thing is said once (no badge repeating a caption, no two buttons for one action). Every list's empty state says what to do next in one sentence, with one button unless the header already has that button.

## Theme-token rule

No hard-coded colours, font sizes, radii or spacing in components. Use `theme.colors`, `theme.spacing`, `theme.radius`, `theme.sizes`, `theme.typography`. Missing a value that the design needs? Add a token, then use it. `accent` (green) is **only** for positive price/stock signals (price drop, in stock, savings); `warning` is for price increases, sold-out and form errors. Touch targets are at least 44 px. The visual reference is `docs/design/kombin-app-tasarimi.pdf`; when it disagrees with a task document, the PDF wins for layout/visuals, the task wins for behaviour and data.

## Types come from `docs/openapi.json`

`src/api/types.gen.ts` is generated by `openapi-typescript`; **never edit it and never hand-write a type the contract already defines**. When the backend changes, copy its new `/openapi/v1.json` over `docs/openapi.json` and run `npm run api:types`. `src/api/models.ts` only re-exports named picks from the generated types. Two contract quirks to know:

- Decimals/ints are typed `number | string` (OpenAPI 3.1 from .NET); the API really sends numbers. Normalize with `toNumber()` from `src/utils/money.ts` before doing arithmetic or formatting.
- `ProblemDetails` in the contract has no `errorCode`/`errors`; the backend adds them. `ProblemBody` in `models.ts` extends the generated type with those two extensions.

## Personas, `personaId` and match scores

- A **persona** is one of the user's styles (Ofis, Hafta sonu, …; at most 6, `MAX_PERSONAS`). Exactly one is _active_ (`GET /me/personas` → `isActive`); the backend activates the first one automatically, later ones are created inactive and activated with `PUT /me/personas/{id}/activate`. `useCreatePersona` does that activation right after creating a persona that came back inactive (a failure is swallowed: the chip row can switch later), so Keşfet switches to the persona the user is training.
- **`personaId` convention:** the active persona's id is the only thing that makes the backend personalise. Send it as `PersonaId` on `GET /catalog/products` (adds `matchScore`, allows `sort=match`) and as `personaId` on `GET /catalog/products/{id}` and on the `/go` link. It needs a bearer token, so calls that carry it use `auth: true`. Logged out, or without personas, send none: Keşfet and detail must keep working.
- `usePersonas()` / `useActivePersona()` (`features/personas/hooks`) are the one way to read it. Signed-in screens wait for the persona query before fetching products, so a list is fetched once, already scored. `withPersona(filters, personaId)` (`features/catalog/filters`) joins it into the query and makes `match` ("Sana göre") the default order; `sort=match` without a persona is dropped (the backend answers 400).
- Match badge "Sana uygun %N": shown only when `matchScore ≥ 70` (`matchBadgeScore`, `MATCH_BADGE_MIN`) on cards, detail and feed; below that nothing is shown.
- **Style control:** Keşfet shows one control "Tarzım: Ofis ▾" (`StyleSwitcher`) that opens a sheet to switch the active style or start a new one; it is hidden while logged out and whenever there is only one style (new styles then start from Profil).
- Card footer: with more than one seller it reads `En ucuzu {cheapestSeller.name} · {n} satıcı` (the seller of the offer behind `lowestPrice`), or `{n} satıcıda en ucuzu` when `cheapestSeller` is `null`; with one seller there is no footer.
- `PUT /me/profile` since Task 13c: a field left out is **unchanged**, an explicit `null` clears it (the audience is the exception: `null` keeps it); the outfit engine reads the weather from the `city`. Always build the body with `toUpdateRequest(profile, patch)` (`features/profile/hooks`), which carries both. The city is set in the measurements sheet ("Şehir", at most 80 characters, placeholder "İstanbul", blank clears it); saving refetches the outfits, so the daily outfit gets its weather pill.
- Swipes: `createSwipeOutbox` (`features/onboarding/swipeOutbox`) batches every 5 swipes, flushes when the screen is left, retries a failed batch once and then drops it silently. Only the first run moves on as soon as the backend says `onboardingCompleted`; re-training a persona runs until the cards are used up.

## Onboarding entry rule

`OnboardingGate` (mounted in `AppProviders`) fires **once per sign-in**: when `GET /me/profile` says `personaCount === 0`, the user is sent to `/audience` (`app/(onboarding)`) instead of the tabs. It does not fire again later in the session (e.g. after archiving the last persona), while already inside onboarding, or after "Atla". Skipping creates nothing and sets `prefsStore.onboardingSkipped`, which is **kept in memory only**: a skipped onboarding is asked again on the next launch. The first run is **two steps**: audience, then 8 swipe cards (`FIRST_RUN_CARD_LIMIT`; re-training asks for 20). After the audience, `AudienceScreen` creates the style silently as **"Tarzım"** (`tr.personaDefaultName`, icon `custom`; an existing "Tarzım" is reused on a 409); there is no naming step and no summary screen: the last card lands on Keşfet (`/done` redirects to `/`). The name step and swipe run as a modal for "Yeni tarz ekle" in the style sheet and "Yeni tarz oluştur" on Profil (`flow=new`) and for "Tarzını yeniden öğret" (`flow=retrain`); `flow`/`returnTo` are route params (`features/onboarding/flow`).

## Buying: `goPath` only

The app never builds or opens a seller URL. Every buy action (the detail bar button and each seller row, which is itself the link: there is no separate "Git") opens `EXPO_PUBLIC_API_URL + offer.goPath + '?src=product_detail' (+ '&personaId=…')` in `expo-web-browser`; the backend records the click and answers `302` to the affiliate URL, which the browser follows. Use `openOffer` / `buildGoUrl` (`features/catalog/buy`); the contract's `OfferResponse` has no seller `url` on purpose. `openOffer` also reports `buy_click { offerId, source }`. A `goPath` that already carries a `src` (a feed post's: `?src=feed&post=…`) is opened as it is, never with a second `src`.

## Push (`src/push`)

- `requestPushPermission()` asks for the OS permission (skipped on simulators via `expo-device`) and, on grant, stores the Expo push token in `prefsStore.pushToken` (memory only) and registers it. It is only called from the contextual sheet "Fiyat düşünce haber verelim mi?", shown **once after the user's first alert** (`usePushPrimer`), and from the "İzin ver" button in the preferences sheet; never on app start.
- `registerPushToken()` → `PUT /me/devices { expoPushToken, platform: Ios|Android, appVersion, deviceName }` (204, idempotent), signed-in only, best effort, **once per token per launch**. `syncPushRegistration()` (run by `PushRegistration` in `AppProviders` on every cold start and sign-in) reads the token **without prompting** when the OS permission is already granted and registers it. Sign-out calls `resetPushRegistration()` so the next sign-in registers again.
- Logout sends the push token in the body (`POST /auth/logout { refreshToken, expoPushToken }`); the backend deactivates that device. If the token is not known yet, logout simply omits it.
- `NotificationHandler` (also in `AppProviders`) shows foreground pushes as a banner (and refreshes the bell/feed) and routes a tap, including the one that cold-started the app, by `data.deepLink`. The backend's push payload **is** the notification's `data` (`deepLink` plus ids): it carries no notification id or kind, so `handlePushTap` (`features/notifications/pushTap`) finds the newest unread feed entry with the same `deepLink` to report `notification_open` and to mark it read; if that lookup fails the screen has already opened and nothing else happens.
- `openNotificationSettings()` opens the OS settings page for the denied state (used by the preferences sheet).
- There is no EAS project id yet, so on a real device `getExpoPushTokenAsync` may fail until `extra.eas.projectId` is configured; the app then simply has no token.

## Notifications (`features/notifications`)

- Route `app/notifications.tsx`, opened from the bell on Keşfet (`NotificationBell`: badge from `GET /me/notifications/unread-count`, refetched on every focus with `useFocusEffect`, joining an in-flight fetch). Signed out, the bell still opens the screen, which shows a login prompt.
- The screen (design screen 06) is a `SectionList` of the feed (`GET /me/notifications`, 30 per page, infinite) grouped Bugün / Dün / Daha önce by device-local day (`groupByDay`), with client-side filter chips Tümü / Fiyat (`PriceDrop`, `AnyChange`) / Stok (`BackInStock`) / Öneri (`NewMatches`); `System` shows only under Tümü. Unread rows are filled cards (green icon square for a price drop, the one positive signal), read rows are outlined.
- A tap runs `useOpenNotification`: `notification_open` event, `POST /me/notifications/{id}/read` (optimistic, only if unread) and `goToTarget` by `data.deepLink`: `kombin://product/{id}` → product detail (`source=notification`), `kombin://matches/{personaId}` → **activates that persona and goes to Keşfet** (there is no persona screen), `kombin://notifications` → the screen itself. `parseDeepLink` accepts only those three shapes.
- The header menu has "Tümünü okundu işaretle" (`POST /me/notifications/read-all`); the sliders button and the Profil row "Bildirim tercihleri" open `PreferencesSheet` (`GET/PUT /me/notification-preferences`): toggles for price/stock/recommendations, weekly maximum 1-7, quiet hours (both times or `clearQuietHours`), and a notice with a link to the OS settings (denied) or an "İzin ver" button (not asked yet). The form edits a local draft and sends **one** PUT on "Kaydet"; times are `HH:mm`, Istanbul time (the backend's `timeZone`).

## Analytics (`src/analytics`)

- `track(name, props)` is fire-and-forget (never awaits, never blocks the UI). Events go into a queue that flushes at **20 events or 15 s after the first queued one**, and on `app_background`; at most 50 per request; a failed batch is tried once more on the next flush and then dropped; the backlog is capped at 500. `POST /api/v1/events` is sent with the bearer token when signed in, anonymously otherwise.
- **Allow-list guard** (`events.ts`): `EventProps` types every call site and `EVENT_KEYS` mirrors the backend README table exactly (event names and property keys; `__tests__/analytics/events.test.ts` repeats that table). In development `track` **throws** on an unknown event, a key outside the event's set, a missing required key, a nested value, or a key named `email`/`name`/`phone`/`address`/`token`; in production such an event is dropped silently. `search` carries `queryLength` only, never the text (nothing emits it yet: there is no search UI). Change the client table whenever the backend's changes. The backend judges events one by one: a rejected one is logged in dev and never costs the rest of the batch.
- `anonymousId` is generated once and kept in secure store (`kombin.anonymousId`), sent **on every event** (not per batch) and in the login/register bodies so the backend attaches the pre-login events to the user. `sessionId` is a new id per cold start.
- Wardrobe and outfit events (Task 13): `wardrobe_add_start { source: camera|library|catalog }`, `wardrobe_add_done { status: Ready|Failed|Timeout, durationMs }` (one pair per photo or catalog add), `outfit_view { kind, status, occasion? }` (once per outfit that comes on screen; **`status` is the outfit's `completeness`** (`Complete`, `NeedsOne`, `CatalogOnly`), because the outfit's own `status` is `Suggested` at view time and says nothing), `outfit_shuffle`, `outfit_feedback { action: Save|Dismiss|Worn|Shuffle, reason? }`, `outfit_gap_click`. They are in the client table and its test, and in the backend allow-list (`AnalyticsEventCatalog`, branch `task-13-analytics-events`); a backend build older than that rejects them one by one (logged in dev, the rest of the batch is unaffected).
- Social events (Task 14): `post_view`, `post_tag_tap`, `post_like`, `post_create_start/done`, `post_report`, `creator_profile_view`, `try_with_wardrobe` (see "Social" below; ids and enums only, never captions, labels or handles; all are in the backend allow-list).
- Pairing events (Task 13c): `wardrobe_pairings_view { companionTotal, hasUnlock }` (once per opened item, when its pairings are on screen) and `wardrobe_unlock_click` ("İncele" on the unlock card). They are in the client table and its test but **not yet in the backend allow-list** (Part A of 13c merged without them), so the backend rejects them one by one until `AnalyticsEventCatalog` lists them.
- Emitted: `app_open` (cold start and each return from the background) / `app_background` / `screen_view` (`AnalyticsTracker`, `usePathname`, uuids replaced by `:id`), `product_view` (detail, once per opened product, `source` from the `?source=` route param: `discover`, `saved`, `alert`, `notification`, `push` or `direct`; build links with `productHref`), `product_list_view` (Keşfet, once per filter set; filter _names_ only), `swipe`, `onboarding_step` (first run only: `audience`, `swipe` with `next`/`skip`, then `done` + `done` when the last card lands on Keşfet), `alert_created`, `buy_click`, `notification_open`.
- Jest replaces `@/analytics` with a no-op in `jest.setup.ts` (the real queue owns a timer); tests of the module itself use `jest.requireActual('@/analytics')`, and screen tests assert on `track`.

## Wardrobe (`features/wardrobe`)

**Purpose: pairing first, tracking in the background.** Tapping a garment answers "what in my wardrobe goes with this, and what one piece would unlock more?" (`GET /me/wardrobe/items/{id}/pairings`). Wear tracking (`wearCount`, `lastWornAt`) stays in the data because the outfit engine uses it, but it is not in the foreground: no wear pills on tiles, no wear button or history on the item page, only the overflow menu. Do not bring a tracker feel back into the grid or the detail page.

**The rule: adding a garment feels instant.** The photo goes up, a card appears in the grid at once in an "İşleniyor" state (shimmer over the photo that is already on the phone), the labels fill in when the backend says `Ready`, and confirming is one tap. Nobody waits on a spinner.

- **Dolap tab** (`WardrobeScreen`, design screen 04): header with the black "Parça ekle" pill (`AddItemSheet`: Fotoğraf çek / Galeriden seç / Kataloğdan ekle), the daily outfit card from 5 pieces (`DAILY_CARD_MIN_ITEMS`), one summary sentence instead of stat cards ("48 parçanla 212 kombin çıkıyor; 3 parçanın henüz eşi yok.", or "Dolabında 48 parça var" while `possibleOutfits` is `null`, "hepsinin eşi var" at 0), the black gap card (first gap's `message` and `unlocksEstimate`; "Önerilere bak" opens `suggestedProducts` as `ProductCard`s; hidden without gaps), filter chips (Tümü, five top-level categories, colour sheet), a 3-column infinite grid with pull-to-refresh, the dashed "+" tile last, and an empty state ("5 parçayla başla"). Logged out it shows a sign-in prompt and calls nothing.
- **The "eşi yok" clause** of that sentence counts finished, categorised pieces whose list `companionCount` is `0` (`isUnmatched`, `useUnmatchedItems`: it reads every page of `GET /items` at 100 per page, the stats response has carried `unmatchedCount` since the backend's 13c, but the card also needs the ids for its filter) and is a filter: pressed, the grid shows only those pieces (client-side, from that same query); while it is on the clause reads "tümünü göster"; pressing it again or any filter chip leaves the filter; at 0 there is no clause to press. These are the pieces the gap analysis should help with.
- **Tiles** (`ItemTile`): background is the item's `primaryColor` at 15 % over the card colour (`colorTint`; the design's saturated tiles would hide black or dark cutouts); under the tile a small muted caption `{companionCount} parçayla gider` (`companionCaption`; "Eşleşen parça yok" at 0; nothing while `Processing`/`Failed` or when `companionCount` is missing: it is on `GET /items` only, so local upload cards have none until the list refetches); `Processing` shows the shimmer and is not tappable; `Failed` shows the warning badge and a tap retries.
- **Add flow** (`addItem.ts`, a plain module over the query client, state in `addStore.ts`): pick/take photo (`picker.ts`, up to 10) → a local card is prepended to every unfiltered cached list at once (`cache.ts`) → `prepareImage` (longer edge to 1600 px, JPEG 0.85, always re-encoded so HEIC becomes JPEG; the file size from `getInfoAsync` is the `sizeBytes` sent) → `POST /items/upload-url` (the card takes the server id and keeps its local photo via `addStore.localUris`) → `PUT` the file to `uploadUrl` by URI (`uploadAsync`, `BINARY_CONTENT`) with exactly the returned headers and **no bearer token** (`putPhoto`) → `POST /items/{id}/process` → `watchItem` polls `GET /items/{id}` every 1.5 s for at most 40 s. `Ready`/`Failed` replace the card and invalidate everything derived from the wardrobe (`invalidateWardrobe`: wardrobe and all outfit queries); a poll that fails is retried, a 404 or the 40 s limit turns the card `Failed` (`Timeout` in analytics). Several photos upload one after another (the "3/10 yükleniyor" pill appears for more than one) while their analyses run in parallel. A card that ends `Failed` prints its reason as a small caption (`addStore.failureReasons`: the backend's `failureReason`, `timeout`, or the upload error). A failed upload leaves a failed card that remembers its photo (`retryPhotos`): a tap sends it again; a server-side failure is retried with `process`. `addFromCatalog` posts `/items/from-product` (`size: null`) and the item is ready and confirmed at once.
- **Confirm sheet** (`ConfirmItemSheet`, mode `confirm`): when an item turns `Ready` **and the wardrobe tab is focused** (`addStore.onWardrobeScreen`, set by `useFocusEffect`) its id joins `confirmQueue` and the sheet opens by itself, one at a time; otherwise only the card updates. Big cutout, category chips from `analysis.categoryCandidates` (top one preselected; `needsCategory` preselects none, asks "Bu parça hangisi?" and keeps Kaydet disabled; "Diğer" lists every leaf category), colour swatches (all 15, live tint), pattern/fit/formality/seasons collapsed under "Detaylar", optional name, a one-line hint for the first known quality warning (`labels.warningHint`). **Kaydet sends a `PATCH` with only what changed; `{}` is the confirmation.** `isGarment=false` shows "Bu bir kıyafete benzemiyor" with "Yine de ekle" (`PATCH {}`) and "Sil" (archive).
- **Item detail = the pairing screen** (`app/wardrobe/[id].tsx`, `WardrobeItemScreen` + `PairingsSection`): the cutout takes 40 % of the window height (`sizes.itemCutoutRatio`), then "Bununla giyilir": one horizontal row per group (Üstler / Altlar / Dış giyim / Ayakkabı / Aksesuar, in the backend's order) of companion tiles; the reason is **not** shown by default, "Neden?" next to the heading reveals one plain line per piece (`reasonLabels`: "Sade bir renk, her şeyle giyilir", …; never colour-theory words); a group with nobody shows a dashed tile "Dolabında buna uyan yok"; a tap opens that piece. Below: "{outfitCount} kombinde yer alıyor", and, when `unlock` exists, the compact black card "Bir {slot} eklersen {unlocksEstimate} kombin daha çıkar" with the product thumbnail, price, cheapest seller and "İncele", which opens the **product detail** (`wardrobe_unlock_click`; buying still happens only there, through `goPath`). The pairings query is separate from the item query: while it loads there are skeletons, a failure shows a retry and leaves the page usable, a 404 (unfinished or uncategorised piece) says to confirm the category first. `useItemPairings` is under `wardrobe`, so any wardrobe change refetches it; the persona is the backend's active one (none is sent). Attributes are collapsed into a "Detaylar" row that opens the confirm/edit sheet (mode `edit`: details open, plus brand search, size and price; a field emptied is sent in `clear`). A link to the product shows when the item came from the catalog. **The header menu (⋯)** holds "Bugün giydim" (`POST /wear`, toast with "Geri al" → `DELETE /wear/{wornOn}`) with the wear count and last worn date under it (nowhere else), Düzenle and "Dolaptan çıkar" (a native confirm, then `DELETE`). **The screen's one primary action** is the bottom-bar button "Bu parçayla kombin yap" (how-to-wear with `wardrobeItemId`).
- Toasts take an optional action (`showToast(message, { label, onPress })`).

## Outfits (`features/outfits`)

- **Daily** (`app/outfits/daily.tsx`, opened by the outfit card on Keşfet and Dolap; the old `/add` route redirects here): `GET /me/outfits/daily?Date&Occasion&Seed`; route params `date` (`today` default, `tomorrow`), `seed`, `occasion`. The backend picks the active persona, so no `personaId` is sent. Header "Pazartesi ofis" (weekday of `outfit.date`, occasion), subtitle "{persona} · {temp}° {weather}", one controls row: the label "Nereye?", the occasion chips (Ofis, Hafta sonu, Gece, Spor, Davet; tapping again clears; a change restarts at seed 0) and the labelled "Başka öneri" button (the shuffle), a 2×2 piece grid (`OutfitPieces`: top, bottom, outerwear, shoes; accessory as a small tile), the narration under it, and the white sheet (`OutfitSheet`).
- **Pieces** (`PieceTile`): wardrobe pieces carry the white "Dolabında var" pill (and no caption repeating it); a gap piece (role `Gap`) has the accent border, "Eksik · {price}" and "En ucuzu {seller}"; the anchor (how-to-wear) has an ink border and "Ana parça". **Sheet:** `Complete` → "Kombini kaydet" + "Bugün giydim" (`POST /{id}/worn`); `NeedsOne` → "Eksik 1 parçayı tamamla", `completionPrice`, a row per gap and "Satın almaya git"; `CatalogOnly` (several gaps) → the rows (each opens its own offer) and save. The contract has no original price on an outfit offer, so the sheet shows no savings figure.
- **Shuffle and seeds** (`seeds.ts`): the shuffle button asks for a new seed (`highest + 1`, so a shuffle after "back" never repeats a skipped outfit), keeps the last 3 seeds for the "Önceki kombin" button, and reports `Shuffle` feedback (best effort). Seed 0 is the plain ranking and is always sent.

A dismissal invalidates the day's outfit queries (the home card asks again). **Empty wardrobe** (`wardrobeEmpty`): the message, the `Shopping` outfit labeled "Mağazadan" with its `totalPrice`, and "Dolabını doldur"; the ✕ closes without asking.

Save and worn patch the outfit in every cached place (`patchOutfit`) instead of refetching; any wardrobe change (`invalidateWardrobe`) and a dismissal refetch the day's outfits.
- **Home card** (`DailyCard` on Keşfet, and on top of Dolap from 5 pieces; design screen 02): today's outfit until noon ("BUGÜN İÇİN"), tomorrow's from noon ("YARIN İÇİN"; `homeCardDay`): `GET /me/outfits/daily?Date=today|tomorrow&Seed=0`, asked for only when signed in **and** `itemCount > 0` (`homeCardState`; the card waits while the stats load, and falls back to the prompt "Dolabına 5 parça ekle, her gün sana kombin hazırlayalım" otherwise). ## Social (`features/social`)

**The rule: a shoppable, price-aware feed, never an Instagram clone.** Every post answers what it is, where it is cheapest and whether it goes with what the viewer owns. No comments, DMs, stories, video, hashtags or post search (the backend has none). Spec: the backend's `docs/design/social.md`, `docs/privacy-notes.md` and README "Social".

- **Where it lives.** The **Akış** tab (`app/(tabs)/feed.tsx`, `FeedScreen`): title with the one primary action "Paylaş", then a "Herkes / Takip ettiklerim" toggle (`FeedSection`; `GET /feed?mode=forYou|following`, pages of 20, `hasMore`; the mode is the URL param `mode=following`). An old Keşfet link `?view=feed` is sent to `/feed`. Signed out: only `forYou` (no token sent); "Takip ettiklerim" shows a sign-in prompt and the query stays off, so the 401 is never provoked. A signed-in feed waits for the personas like the product list and sends the active `personaId`. The feed query key includes signed-in or not (`likedByMe`, `inWardrobe`, `matchScore` are per viewer).
- **Post card** (`PostCard`, design screen 09). Author row (the display name alone on the first line; the "Kreatör" chip when `isCreator`, `@handle` and "Sana uygun %{matchScore}" (from 70) on the second, which truncates first; "Takip et" / "Takip ediliyor"; the author's own posts have no follow button; a tap opens `/creators/{handle}` for a creator, `/users/{id}` otherwise). Photo at its `aspect` (`PostPhoto`) with a dot per confirmed tag at its box centre; an **outfit post** (`image: null`) draws a square collage from `tags[].imageUrl` at their x/y/w/h boxes. **Band:** "Bu kombin toplam {price} · {n} parça · {k}'si dolabında var" (`postBand`: only formats the backend's per-viewer `summary`; no price when none is known, no owned part when `ownedCount` is `null`, "hiçbiri dolabında yok" at 0). A dot opens `TagSheet` (name, price, "En ucuzu {seller}", `inWardrobe` exact/similar, "Satın al") and sends `post_tag_tap`; the band opens the same sheet with every piece. Like (optimistic, rolls back, `post_like`), "save" (there is no post save: it saves the tagged `productId`s through `/me/saved`, or removes them again when all are saved), accent "Dolabımla dene" (`TrySheet`: `POST /posts/{id}/try`, groups and outfits, a missing piece with price and "Satın al"; `try_with_wardrobe`; a 409 `Social.NothingToTry` says nothing came out), caption, and the **disclosure line whenever `disclosure` is present**. ⋯ menu: "Şikayet et" (reasons Nudity, Violence, Hate, Harassment, Spam, Scam, Other → `post_report`; **409 → "zaten şikayet ettin"**) and "Engelle" (native confirm, `POST /users/{id}/block`, then that author's posts leave every cached list at once: `removeAuthorPosts`). Signed-out taps on like / follow / try / report / block go to the login screen.
- **Buying: `goPath` only, and `src` is not added twice.** A post offer's `goPath` already reads `/api/v1/go/{offerId}?src=feed&post={postId}` (the post is what a creator is paid for). `buildGoUrl` leaves a link that already has a `src` as it is (`ClickSource` has `feed`). The app never sees a seller URL; `try` gap pieces use the same `openOffer`.
- **Photos: cache key = post id.** Post photos are presigned URLs that expire after an hour and change on every response; React Native's `Image` caches by URL. `stableImageUrl(postId, url)` (`imageUrl.ts`) keeps the first URL seen per post for 45 minutes, so a refetch does not download the photo again (no new package: `expo-image` would have been the other way).
- **Post flow** (`app/posts/new.tsx`, `CreatePostScreen`; a modal; `?postId=` resumes an unfinished post from "Gönderilerim"): consent → pick (camera, library, or "Kayıtlı kombinden paylaş") → upload and check → tag editor → caption + visibility → publish → done.
  - **Consent first.** `GET /social/consent` (`{version, text, acceptedAt}`); while `acceptedAt` is `null` only the consent text and "Okudum, kabul ediyorum" are shown (`POST /social/consent {version}`), nothing can be picked or uploaded. A 403 `Social.ConsentRequired` at `upload-url` (a new version) sends the user back to it.
  - **Upload** (`createPost.ts`): `prepareImage` (the wardrobe's: longer edge 1600 px, always re-encoded to JPEG, which turns HEIC into JPEG **and drops EXIF/GPS on the phone**) → `POST /posts/upload-url` → `putPhoto` (the wardrobe's: `uploadAsync` from `expo-file-system/legacy`, exactly the returned headers, no bearer token) → `POST /posts/{id}/process` → `watchPost` polls `GET /posts/{id}` every 2 s for at most 120 s. `Draft` → tag editor; `Blocked` / `Failed` → the backend's `statusMessage`; `NeedsReview` → "incelemede" (no editing while it waits for a person); a timeout points at "Gönderilerim".
  - **Tag editor** (`TagEditor`, pure logic in `tagDraft.ts`). It starts from the proposal dots, which are **all unconfirmed**; the author drags (a `PanResponder`, needs a device to check), deletes or adds (up to 6) and names each dot: "Dolaptan" (`GET /me/wardrobe/items`, ready pieces, narrowed by the proposal's category, can be widened), "Üründen" (`GET /catalog/products` filtered by the proposal's category and colour, can be widened) or "Bilinmiyor" (optional label, 60 characters). A saved outfit's pieces carry a suggested target; it still needs the author's "Öneriyi onayla" tap. **"Devam" stays off while any dot is unconfirmed, and `toPublishTags` only ever returns dots with a choice**: an unconfirmed proposal is never serialised, even if the screen let it through (`__tests__/features/social/tagDraft.test.ts`). A product-picker query must not live under the `social` query-key prefix (those caches are walked looking for posts).
  - **Publish step:** caption up to 300, visibility "Sadece ben / Takipçilerime / Herkese açık" (`VisibilityPicker`), **default "Sadece ben"** (`DEFAULT_VISIBILITY`). `PUT /posts/{id}/publish`; a 409 `Social.PostProcessing` / 400 `Social.InvalidTagTarget` have their own messages. `post_create_start { kind, source }` at the pick, one `post_create_done { kind, status, tagCount, visibility?, durationMs }` per flow: `Live` / `NeedsReview` after a publish, `Blocked` / `Failed` when the check ends so, `Cancelled` when the screen is left first.
  - "Kayıtlı kombinden paylaş" is `POST /posts/from-outfit {outfitId}`; it returns a `Draft` outfit post (no photo) whose pieces are proposals with collage boxes, then the same editor (a list; there is no photo to drag over).
- **Profiles and creators.** `/users/{id}` (`GET /users/{id}` + `/users/{id}/posts`, follow button), `/creators/{handle}` (`GET /creators/{handle}`: handle, bio, link (only `http(s)` links open, in `expo-web-browser`), disclosure, and the first page of posts, which seeds the post list so it is not asked for twice; `creator_profile_view { creatorId }` once), `/posts/{id}` (one post, `post_view` source `link`). Profil rows: "Gönderilerim" (`/posts/mine`: every status with the backend's `statusMessage`, a fallback hint for `NeedsReview` / `Hidden` / `Failed`, delete after a native confirm, "Devam et" on a draft), "Kazançlarım" (`/profile/creator`, **shown only when `GET /me/creator/stats` answers; a 403 means not a creator and is not retried**; the amount is **always labelled "tahmini"** with how it is computed, and `confirmedEarnings` is separate), "Engellenenler" (`/profile/blocks`, `GET /me/blocks`, unblock).
- **Analytics.** `post_view { postId, source: feed|profile|creator|mine|link, position? }` once per post per list, from the list's viewability callback (`usePostViewTracking`); `post_tag_tap`, `post_like`, `post_create_start/done`, `post_report`, `creator_profile_view`, `try_with_wardrobe` (see `events.ts`; all are in the backend allow-list). Post and creator **ids and enum values only, never captions, labels or handles**.
- **Cache** (`cache.ts`): `patchPost`, `patchAuthorPosts` (follow state), `patchProfile`, `removeAuthorPosts` (block), `removePost` (delete) rewrite every cached place a post can be (feed pages, profile lists, mine, the creator page, a single post) without refetching. Social queries live under `queryKeys.socialAll`.

## Social sign-in (`features/auth/externalSignIn.ts`)

- `signInWithGoogle()` / `signInWithApple()` get an ID token on the device and call `POST /auth/external { provider: 'google'|'apple', idToken, displayName?, deviceName, anonymousId }`; the returned tokens go through `completeSignIn`, exactly like a password login (same session store, same refresh path). Apple's name arrives only on an account's first sign-in and is sent as `displayName`; the backend uses it only when it creates the account.
- Both return `null` when the user closes the sheet (Google `SIGN_IN_CANCELLED` / a `cancelled` response, Apple `ERR_REQUEST_CANCELED`): no message. Backend codes map to Turkish in `externalSignInMessage` (`Identity.ExternalTokenInvalid`, `ExternalEmailMissing`, `ExternalProviderDisabled`, `ExternalProviderUnavailable`); anything else is a generic line.
- **The native modules are loaded with `require()` inside the functions**, never at the top of a file (not `import()` either: Jest cannot run it). Loading them eagerly would crash Expo Go, the web export and Jest. `ExternalSignInButtons` (top of the login and register screens, with the "veya" divider) renders nothing in Expo Go (`Constants.appOwnership === 'expo'`) or on web; the Apple button (`AppleAuthenticationButton`, so it passes review) appears only on iOS and only when `isAvailableAsync()` is true (`loadAppleAuthentication`).
- `isNewUser` needs no routing of its own: both screens do `router.dismissTo('/')` and `OnboardingGate` sends an account with no persona to onboarding, exactly as after a registration.
- Client ids come from `.env` (`EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID`, `EXPO_PUBLIC_GOOGLE_IOS_CLIENT_ID`, placeholders in `.env.example`), never from source. The only id in `app.json` is the reversed iOS client id as the Google plugin's `iosUrlScheme`. A change to either id needs a new native build.
- `auth_external { provider, isNewUser }` is in `events.ts` and its test but **nothing emits it** until the backend's `AnalyticsEventCatalog` lists it (TODO in `externalSignIn.ts`).

## Session and refresh behaviour (summary)

- `request(path, { auth: true })` sends the bearer token. Public catalog calls send none, so Keşfet and product detail work logged out.
- Every request carries `Accept: application/json` and a fresh `X-Correlation-ID` (uuid v4); failed requests log the id in dev.
- Errors are parsed from `application/problem+json` into `ApiError { status, errorCode, detail, fieldErrors, correlationId }`; `status 0` means the network was unreachable. Forms map `fieldErrors` onto fields (`features/auth/formErrors.ts`), otherwise show `detail`.
- Proactive refresh: if the access token has < 60 s left, refresh before sending. On a 401: refresh once, retry the request once. Concurrent refreshes share **one** in-flight promise (refresh tokens are single-use/rotated). A second 401 or a rejected (4xx) refresh clears the session and the root layout routes to login; a network failure during refresh does **not** log the user out.
- Bootstrap (`bootstrapSession`, run from `AppProviders`): stored refresh token → refresh → `GET /me` → ready. The native splash stays up until fonts and the session are ready, so a logged-in user never sees the login screen flash.
- Logout: `POST /auth/logout` with the refresh token and the push token (best effort), then always clear local state.

## How to add a screen

1. **Route file** in `app/` (e.g. `app/(tabs)/wardrobe.tsx`) that only exports/wires the screen from `src/`.
2. **Screen component** in `src/features/<feature>/<Name>Screen.tsx`.
3. **Feature folder**: its components, filters/helpers, and copy added to `src/i18n/tr.ts`.
4. **Query hook** in `src/features/<feature>/hooks.ts` using `queryKeys` and an endpoint function in `src/api/endpoints/<feature>.ts` (typed from `models.ts`). Add the query key to `src/api/queryKeys.ts`.
5. **Test** in `__tests__/features/<feature>/` — at least one render test of the screen (mock `@/api/endpoints/...`; helpers in `__tests__/testUtils.tsx`).

## Development build (replaces Expo Go)

Expo Go is no longer the dev target: Google and Apple sign-in are native code. Build and install a development client once (and again whenever a native dependency, a plugin or a client id changes), then run Metro against it:

```bash
eas build --profile development --platform android   # installable .apk (iOS: --platform ios, needs an Apple developer account)
npx expo start --dev-client
```

In Expo Go the app still opens and the e-mail form works, but the social buttons are hidden.

## Working rules

- **Do not abstract until the third repetition.** Two similar pieces of code are fine; extract on the third.
- **Do not commit unless asked** (a task document that says "commit on the branch" counts as asking). Leave the working tree for review otherwise.
- Keep `npm run lint`, `npm run typecheck` and `npm test` green before declaring work done.
- Jest cannot run Reanimated/worklets natively: `jest.config.js` uses Reanimated's resolver, `jest.setup.ts` mocks Reanimated (its official mock), the worklets runtime holder and `ReanimatedSwipeable`, and `renderWithQuery` wraps screens in `GestureHandlerRootView`. The deck's drag gesture therefore is not covered by tests (the buttons path is); check it on a device. The same goes for the outfit sheet's swipe-down (a `PanResponder`).
- `jest.setup.ts` replaces `expo-image-picker` and `expo-image-manipulator` with stubs (no native module under Jest); the add-flow tests (`__tests__/features/wardrobe/addItem.test.ts`) mock the wardrobe endpoints and drive the polling with fake timers. `outfit` fixtures (`outfit`, `needsOneOutfit`, `dailyOutfit`) auto-number their ids: give an outfit an explicit `id` when a test saves or wears it, or the cache patch will not find it.

## Out of scope (do not add)

Comments, DMs, stories, video, hashtags and post search (the backend has none), a post-level save (saving a post saves its tagged products), editing the tags of a live post, creator self-service, payouts. Push _delivery_ (the backend sends; the app only registers and handles taps), offline cache/persisted queries, crash reporting and any analytics beyond the allow-listed events above, deep links/universal links beyond routing a push tap by `data.deepLink`, any UI kit or styling library, Redux/MobX or context-based global stores, i18n libraries, `expo prebuild`/native code, social login, dark mode.
